# Быстрый запуск и надёжное обновление индексов

Дата: 2026-10-30. Реализовано; конфигурация, свежесть индекса и восстановление описаны в `docs/INDEXING.md`.

## Цель и исходное состояние

Заметки, добавленные или изменённые в Obsidian, по SMB/NFS, через Git, web или MCP, должны попадать в поиск без перезапуска. Обычный запуск не должен ждать полного перечитывания всех заметок. Поиск не должен выдавать незавершённую индексацию за достоверные «0 результатов».

Сейчас `initSearch()` полностью перестраивает MiniSearch до запуска HTTP. Затем отдельно строятся граф ссылок и индекс файлов. Это устранило восстановление устаревшего снимка, но повторно читает заметки. Watcher запускается после построения с `ignoreInitial: true`, поэтому остаётся окно между обходом и началом наблюдения. Обработчики событий работают независимо, `upsert()` удаляет запись при любой ошибке чтения, периодической сверки нет. При fallback native → polling новый watcher не сохраняется в переменной shutdown. SearchPanel запрашивает результаты при изменении запроса, но не после обновления индекса.

Для сетевых файловых систем предусмотрены polling и периодическая сверка; задержка обновления зависит от файловой системы и настроек.

## Что берём из Obsidian

Официальная документация подтверждает сохранение metadata cache в IndexedDB между запусками и синхронизацию кеша с файлами: <https://obsidian.md/help/data-storage>. Она не раскрывает точный алгоритм хеширования и внутренний полнотекстовый индекс. Поэтому переносим архитектурный принцип, а не заявляем копирование внутренней реализации.

WebObsidian хранит собственный серверный кеш в DATA_DIR. Не читает и не модифицирует IndexedDB или `.obsidian` оригинального приложения. Markdown остаётся источником истины.

## Варианты

1. Полная пересборка при старте + текущий watcher: простой вариант, но задерживает запуск и не восстанавливает пропущенные события во время работы.
2. **Рекомендуется: сохранённый снимок + реестр файлов с хешами + очередь событий + фоновая сверка.** Сохраняет MiniSearch и существующий стек, решает запуск и актуальность. Это предложение исполнителя, а не утверждение о деталях Obsidian.
3. SQLite/FTS вместо MiniSearch: полезно при доказанной нехватке памяти или слишком дорогой сериализации, но сейчас добавляет миграцию и риск изменения поиска. Отдельная будущая работа после измерений.

## Контракт поведения

- С валидным кешем: ранний запуск HTTP и интерфейса; восстановление кеша, затем фоновая сверка. До завершения сверки интерфейс показывает «Проверка изменений», сохранённые результаты явно предварительные.
- Без кеша/при повреждении: интерфейс доступен, статус «Индексация». Поиск до готового индекса возвращает 503 `INDEX_NOT_READY`, а не пустой успешный ответ. Прямое чтение заметок продолжает работать, если хранилище доступно.
- После сверки: обработка очереди событий и регулярный контроль. Изменения вне приложения учитываются автоматически.
- Ручная полная перестройка обслуживает поиск по предыдущему индексу со статусом `rebuilding`; публикация нового состояния происходит целиком. На первом запуске предыдущего состояния нет.
- При недоступности NAS/ошибках чтения: сохраняется последняя успешная версия индекса, статус `degraded`, повторные попытки. Нельзя считать ошибку обхода пустым хранилищем.
- Протоколы MCP stdio и Streamable HTTP, инструменты, права ключей и поисковый синтаксис сохраняются. REST/MCP ответы поиска получают дополнительное поле `index` со статусом. MCP до окончания начальной сверки возвращает понятную повторяемую ошибку `INDEX_NOT_READY`; после неё при деградации явно помечает результаты как потенциально устаревшие.
- Готовность относится ко всем производным данным: tasks/tags/properties/backlinks/graph/resolve и разрешению вложений, включая MCP. До первой успешной сверки текущего поколения эти операции возвращают `INDEX_NOT_READY`, а не пустые коллекции/null. Единственное исключение — web-поиск с явно предварительным кешем. UI при неготовом resolve не предлагает создать якобы отсутствующую заметку. При последующей деградации сохраняются прежние данные и общее предупреждение; для MCP tags/backlinks добавить статус без удаления существующих полей. Прямые файловые операции, не зависящие от индекса, не блокировать.

## Архитектура

### Единый координатор

Сервис indexing владеет watcher, очередью, сверкой, снимком и состоянием. События watcher и уведомления после успешных записей web/REST/MCP проходят через него. Очередь объединяет повторы по пути; обработчик сверяет текущее состояние файла, а не слепо применяет старый тип события. На первом этапе один обработчик чтения/публикации, чтобы ограничить нагрузку на NAS и исключить гонки.

Обновление читает и разбирает Markdown один раз. Из одного результата обновляются поиск, теги, свойства, задачи и исходящие ссылки; индекс вложений обновляется без чтения бинарного содержимого. Реестр хранит все видимые файлы. Правила скрытых папок, `node_modules`, trash и допустимых symlink должны совпадать для обхода и watcher; существующие ограничения allowedRoots сохраняются.

Watcher включается до обхода. Дождаться `ready`, сохраняя события в очередь, выполнить сверку и обработать накопленное. Полные построения и сверки не перекрываются. Поколение vault и номера событий не дают старым чтениям и снимкам перезаписать более новые данные. Если буфер достиг 10 000 уникальных путей, установить `needsReconcile` и провести ещё один обход вместо бесконечного роста памяти.

### Реестр и снимок

На файл: относительный путь, размер, mtime, ctime и необязательные dev/ino, SHA-256 полных байтов Markdown, время последнего успешного чтения и проверки хеша. Метаданные — дешёвый сигнал изменения, не доказательство равенства. Хеш не заменяет version API: существующий короткий `base_version` остаётся совместимым.

Снимок формата v1 содержит версию схемы/парсера, идентификатор канонического vault и политики обхода, поколение, реестр и согласованные данные поиска, задач, свойств, ссылок и файлов. Полный текст второй раз в кеше не хранить; сохранять необходимые производные данные. Валидный пустой vault поддерживается.

Запись: временный файл рядом с конечным → flush/close → rename; при сбое оставить прежний файл. Не сохранять снимок из частично завершённой публикации. Сохранять после 2 секунд покоя, но не реже одного раза за 30 секунд при непрерывных изменениях; финальная попытка при shutdown в пределах общего тайм-аута. Ошибка сохранения видна в статусе, но не ломает работу поиска в памяти.

Старый `qmd-index.json` не содержит достаточных данных: оставить его нетронутым для отката; новая версия один раз строит новый `vault-index-v1.json`. Несовпадение vault/версии/политики либо повреждение означает промах кеша, а не доверие старым результатам.

MiniSearch сейчас использует `autoVacuum:false` из-за ранее наблюдавшегося падения; это сохранить. Раньше очистку старых терминов обеспечивал каждый restart. Теперь учитывать число replace/discard с последнего полного построения и сохранять счётчик в снимке. При достижении `max(500, ceil(indexedNotes * 0.2))` запросить фоновый rebuild через ту же очередь; также раз в 24 часа, если счётчик ненулевой. Одновременно только один rebuild; успешное завершение обнуляет счётчик, ошибки видны и не вызывают непрерывный цикл повторов (повтор через 30 минут). Проверить длительное редактирование/удаление и повторные рестарты на рост памяти. Если безопасный rebuild не укладывается в лимиты, это блокер выпуска кеширования, а не повод без проверки включать autoVacuum.

### Обнаружение изменений и хеши

- Сохранить `WEBOBSIDIAN_WATCH=auto|polling`; auto означает native с fallback при ENOSPC/EMFILE, не автоматическое распознавание NFS.
- Значения по умолчанию: polling Markdown 1000 ms, binary 3000 ms, debounce 250 ms с максимальным ожиданием 2000 ms; awaitWriteFinish 300 ms/100 ms.
- Быстрая сверка метаданных каждые 60 секунд, а также при запуске, восстановлении watcher и ручном запросе. Читать содержимое новых/изменённых файлов. Событие change заставляет проверить хеш даже при одинаковых stat.
- Полная фоновая проверка хешей Markdown раз в 30 минут, начиная после первой сверки; один проход за раз, последовательное чтение с уступкой event loop между файлами. На снимке фиксировать время последнего завершённого прохода; после рестарта продолжить проверку, если она просрочена.
- При одинаковом хеше обновлять метаданные, не перезапускать парсер. При перемещении всё равно обновить зависимые от пути title/id/links. Хешировать полные байты, хотя индекс тела сейчас ограничен 100 000 символами.
- Stat до/после чтения; при изменении повторить позже. Retry через 1/5/30 секунд, затем следующая сверка. Совпадение stat не является абсолютной гарантией против внешнего писателя; последующие события и аудит обеспечивают сходимость после завершения записи.
- Удаления после события unlink подтверждать проверкой отсутствия и успешным обходом родителя. Отсутствие при периодическом обходе подтверждать двумя успешными проходами с интервалом не менее 5 секунд. Ошибки обхода запрещают удаления в затронутом поддереве. Подозрительное исчезновение >=50% файлов или всех файлов переводит состояние в degraded до повторной успешной проверки через 30 секунд; это предохранитель, не доказательство доступности mount. На NFS различение настоящего пустого vault и пустой точки монтирования требует контроля mount оператором, ограничения явно документировать.
- После восстановления NAS повторить сверку и аудит. Задержка видимости NFS остаётся внешним ограничением. 60 секунд/30 минут — частота проверок, не жёсткий SLA: добавляется время обхода, очереди и кеширования NAS.

### Жизненный цикл, интерфейс и совместимость

Координатор закрывает именно текущий watcher после fallback, все таймеры и очередь при shutdown. Смена vault через настройки закрывает старое поколение, очищает связанные кеши и запускает новое; результаты разных vault никогда не смешиваются. Перед переключением согласовать уже начатые записи с существующей очередью vaultmutations.

`GET /api/index/status` (сессия) возвращает phase, наличие кеша, generation/revision, режим watcher, размеры очереди и индекса, время последней успешной сверки/аудита, количество ошибок. Без содержимого заметок, ключей и абсолютных путей. `/healthz` остаётся проверкой процесса, отдельный статус показывает готовность поиска.

WebSocket `index` отправляется после публикации изменений, с ограничением частоты 250 ms. Старые `fs` события сохраняются для редактора/дерева. SearchPanel обновляет активный запрос и snippets по revision, игнорирует запоздавшие ответы старых запросов. После reconnect — получить status и повторить поиск. Ошибка сети/индекса не отображается как «0 notes».

В существующих настройках добавить состояние, «Проверить изменения» и «Перестроить индекс». Сохранить совместимость существующего POST `/api/reindex` с ответом `{ok:true}` после завершения; для нового неблокирующего UI добавить POST `/api/index/jobs` с `{mode:'reconcile'|'rebuild'}` → 202 `{jobId}`. Повторный запрос того же выполняющегося вида возвращает тот же jobId, операции сериализуются; полный rebuild покрывает ожидающий reconcile.

## Ограничения и измерения

Сохранить Node >=22.12, TypeScript, MiniSearch, Chokidar, Vitest; без новой БД в первом этапе. Production сейчас ограничен 384 MiB контейнера и 256 MiB heap: измерить максимум при двойном состоянии для rebuild и при JSON restore/serialize. Если не укладывается, пересмотреть формат/способ построения до развёртывания, не увеличивать лимиты молча. Большой синхронный JSON.parse может задерживать event loop; ранний listen сам по себе не доказывает быстрый UI.

Проверить рабочий объём и синтетический vault 10 000 заметок с зафиксированным распределением размеров. Сравнить холодный/тёплый запуск, число прочитанных тел до готовности, HTTP latency во время построения, RSS/heap, нагрузку polling. Критерий тёплого запуска: ноль чтений неизменённых тел для начальной сверки и отсутствие ожидания полного rebuild для открытия UI. Первичная индексная база и глубокий аудит всё равно требуют чтения файлов.

## Не входит

Семантический поиск, embeddings, чтение содержимого PDF/картинок, изменение формата заметок, механизмов авторизации или маршрутизации Perplexity. Не обещаем мгновенную свежесть при недоступном/кеширующем NAS и не копируем закрытые внутренние форматы Obsidian.
