# Диагностика и ревью загрузчика плагинов

Дата: 2026-10-30. Read-only ревью и предложение исправлений; production-код, настройки и плагины не менялись.

## Проверенный диагноз

Приложение с действующей CSP возвращает `script-src 'self' 'nonce-…'` без разрешения строкового исполнения. `web/src/lib/plugins.ts:138` использует `new Function`. Это подтверждённый конфликт.

Изолированный Electron/Chromium запускал настоящий загрузчик, собранный esbuild, с синтетическим плагином и подменённым API. Пользовательские плагины не исполнялись, реальные заметки не использовались.

| Сценарий | Результат |
|---|---|
| CSP как на сервере + корректный простой плагин | `EvalError`, событие `securitypolicyviolation`, blockedURI=`eval`, плагин не стартовал |
| Тот же плагин, контрольная страница без CSP | onload выполнен, ошибок нет |
| Ответ asset HTTP 401 с HTML, контрольная страница | `SyntaxError: Unexpected token '<'`; ошибочно показано incompatible API |

Доказательства и воспроизводимый скрипт: `.superpowers/sdd/2026-10-30-plugin-review/browser-probe.mjs`, `browser-evidence.json` (локальные gitignored диагностические файлы). Первые попытки тестового harness завершались при закрытии первого окна; после добавления обработчика window-all-closed все три сценария завершились и дали таблицу выше.

Вывод: ранее названная причина CSP подтверждена. Она объясняет общий ранний барьер исполнения, но не доказывает, что после его устранения заработают реальные плагины. Стек ошибки из пользовательского браузера не снимался; конкретные последующие исключения Templater пока не воспроизведены.

## Фактически включённые плагины

Прочитаны только manifest, перечень включённых id и статические require в main.js на сервере. data.json и заметки не читались. Версии на момент проверки:

| Плагин | Версия | Найденные require |
|---|---|---|
| Advanced Canvas | 6.0.0 | obsidian, @codemirror/view |
| Automatic Table Of Contents | 1.8.0 | obsidian |
| Editing Toolbar | 3.2.7 | obsidian |
| Templater | 2.18.1 | obsidian, util, child_process, @codemirror/language, @codemirror/state |

У всех четырёх isDesktopOnly=false. Значение false не означает совместимость с WebObsidian. Текущий require принимает только `obsidian`. Статический require может находиться в условной ветке, поэтому перечень зависимостей не равен доказанному стеку падения. Templater также может требовать динамического исполнения пользовательских шаблонов: отдельная проверка обязательна, даже если загрузчик main.js исправлен.

## Findings

Приоритет P1 означает исправить до разрешения работающего общего загрузчика; P2 — функциональный дефект, включённый в тот же план.

1. **P1: CSP блокирует все попытки строкового исполнения.** `web/src/lib/plugins.ts:138`, `server/src/index.ts:99`. Даже минимальный совместимый плагин не стартует. Подтверждено браузером.
2. **P1: create перезаписывает существующий файл, modify обходит защиту конкурентной записи.** `web/src/lib/plugins.ts:42–45`; сервер разрешает безусловную запись при отсутствии baseVersion (`server/src/routes/files.ts:177–190`). create должен использовать baseVersion=""; modify должен отправлять версию прочитанного состояния и явно обрабатывать конфликт.
3. **P1: включение/выключение не соответствует runtime.** `web/src/components/Settings.tsx:475` меняет флаг, но не запускает/выгружает экземпляр; `web/src/App.tsx:81` грузит только при старте. Нет unload при смене vault/logout. После исправления CSP выключенный плагин сможет продолжать работать до refresh.
4. **P1: «успешно загружен» не означает работоспособность.** `web/src/lib/plugins.ts:80–87`: addCommand, Markdown processors, views, settings и другие регистрации — пустые методы. Events не подключены к реальным изменениям workspace/vault. Утверждение интерфейса «most metadata/Markdown plugins work» (`Settings.tsx:481`) не обосновано.
5. **P1: установка может повредить общую desktop-установку.** `server/src/services/plugins.ts:120–124` пишет новый manifest до завершения скачивания main.js/CSS в общий `.obsidian/plugins/<id>`. Ошибка скачивания оставляет смешанные версии; отсутствие styles.css в новой версии сохраняет старый CSS. data.json нельзя заменять вместе с кодом.
6. **P2: данные плагина молча теряются.** `web/src/lib/plugins.ts:84–85`: loadData всегда возвращает {}, saveData ничего не делает. Изолированный вызов saveData→loadData подтвердил потерю результата. Нужен отдельный web storage с честным поведением.
7. **P2: нет lifecycle и отката неудачного старта.** `web/src/lib/plugins.ts:69–74,141–142`: события/интервалы/дети не освобождаются, экземпляр не сохраняется до окончания onload. Повторные одновременные загрузки не объединяются. Ошибка onload может оставить ресурсы.
8. **P2: ложная готовность workspace и неверные контракты shim.** `web/src/lib/plugins.ts:47–49,57,99–102`: getMarkdownFiles не фильтрует Markdown, getAbstractFileByPath создаёт фиктивный TFile для отсутствующих файлов и папок, onLayoutReady выполняется сразу, цепочки Setting.setValue().onChange() ломаются. App запускает восстановление дерева/workspace без ожидания перед plugins.
9. **P2: диагностика скрывает исходную ошибку.** `web/src/lib/plugins.ts:130,160–166`: нет проверки HTTP status; CSP, сеть, синтаксис и API сообщаются одной фразой; ошибка списка подавляется. Несколько одинаковых toast перекрывают друг друга и повторяются на каждом refresh.

Независимое ревью подтвердило пункты 2–9. Дополнительный изолированный probe реального shim подтвердил пустой loadData после saveData, отсутствие baseVersion в create/modify, фиктивный TFile, синхронный onLayoutReady и падение цепочки Setting. Это функциональное ревью выбранного компонента, не полный аудит безопасности репозитория.

## Предлагаемый подход

1. Просто добавить unsafe-eval в основную CSP: открывает первый барьер, но оставляет все остальные дефекты и распространяет изменение на всю страницу. Не рекомендуется.
2. **Рекомендуется: доставка исполняемого модуля с того же origin + явно ограниченный web API.** Сервер формирует проверенный по синтаксису ESM-модуль с CommonJS factory, браузер импортирует его через import(URL). В основной странице остаётся текущая CSP. Не исполнять main.js на сервере. Ограниченные возможности описываются в матрице совместимости; неподдержанные вызовы дают явную причину отказа.
3. Отдельный изолированный runtime с RPC: нужен для более широкой совместимости и иных разрешений, но требует проектирования обмена данными/DOM/editor. Отложить как отдельную работу; не обещать запуск Node/Electron плагинов в обычном браузере.

Модуль, исполняемый в основной странице, получает доступ её JavaScript к DOM и API. Это доверенный установленный код, не sandbox. Не превращать transpilation endpoint в публичный приём произвольного кода; только auth-gated установленный/включённый id с проверкой пути, версии и текущего vault. Включение внешних плагинов остаётся явным действием пользователя.

## Границы исправления

- Первая поставка: достоверная диагностика и ограниченный рабочий runtime; не заявлять полную совместимость Templater/Canvas по одному успешному onload.
- Неподдерживаемые возможности, включая Node child_process и динамическое выполнение шаблонов, явно обозначать; не предоставлять серверное выполнение команд.
- Данные и предпочтения web-плагинов хранить в DATA_DIR по vault/id отдельно от desktop data.json. При необходимости будущего импорта desktop-настроек предусмотреть явный импорт копии.
- Обнаруживать существующие desktop plugin bundles только для чтения. Новые установки/обновления web хранить в DATA_DIR; изменение общей desktop-установки не должно быть побочным эффектом кнопки Install.
- Авторизацию, индексацию и MCP сохранить. Не отключать плагины в desktop community-plugins.json и не менять его data.json.
