# Совместимость отображения с Obsidian — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** приблизить отображение и редактирование существующих заметок к Obsidian, исключив потерю видимого содержимого и случайное выполнение разметки внутри примеров кода.

**Architecture:** сохранить CodeMirror для редактирования; объединить правила диалекта, контекстные границы и преобразования web/server. Live, Reading и HTML Preview получают отдельные адаптеры с явно заданными различиями. Внедрять по группам синтаксиса, без полной замены редактора одним HTML-рендерером.

**Tech Stack:** TypeScript, CodeMirror 6/Lezer, unified/remark/rehype, React, Electron browser fixtures, node:test/Vitest.

**Spec:** [PRD.md, FR-2](../../../PRD.md), запрос пользователя «максимально похожим на оригинал», контракт ниже. Выполнение начато по поручению пользователя; первая критичная группа реализована. [Журнал выполнения и ограничения](2026-10-29-rendering-parity-progress.md). Незакрытые пункты ниже остаются в работе.

## Границы и критерий совместимости

- Проверяем Source, Live с курсором внутри/снаружи конструкции, Reading, отдельный Preview, вложенные заметки и публичный HTML. Таблицы — отдельный контекст внутри этих режимов.
- Исходный Markdown не меняется при просмотре, переключении режимов, перемещении курсора, загрузке вложений и изменении ширины окна.
- Различия режимов допускаются там, где они есть в Obsidian: показ исходной разметки при редактировании, комментарии, inline-сноски. «Одинаково во всех режимах» не является целью само по себе.
- Эталон: чистый временный vault Obsidian без сторонних плагинов, зафиксированные версия, тема, шрифт, размер, масштаб, ширина и настройка Strict Line Breaks. Пользовательский скриншот — эталон для `<LS_BEN>` и его красной подсветки, но не спецификация всех конструкций.
- Тестовые заметки синтетические. Реальный vault, публикация, commit/push и deployment требуют отдельного поручения. Существующие изменения панели цвета сохраняем.
- При неоднозначности сверяем поведение с приложением, а не выводим его из цвета токена или отдельного регулярного выражения.
- Совместимость HTML не требует разрешать выполнение произвольного JavaScript. Разрешённое форматирование и очистка HTML должны быть согласованы между путями.

## Как устроено сейчас

| Путь | Реализация | Особенность |
|---|---|---|
| Source | `web/src/components/Editor.tsx`, `web/src/lib/highlight.ts` | CodeMirror, подсветка синтаксического дерева |
| Live | `web/src/lib/livePreview.ts` | дерево Lezer + многочисленные проходы regex + замещающие widgets |
| Reading | тот же `Editor.tsx`/`livePreview.ts` | переключён readonly и отключено раскрытие исходника курсором; семантика почти полностью унаследована от Live |
| Preview | `web/src/lib/markdown.ts`, `web/src/components/Preview.tsx` | regex до remark → rehype raw → sanitize → HTML; затем DOM-постобработка |
| Вложенные заметки | Live `NoteEmbedWidget` → `renderMarkdown`; Preview `expandEmbeds` | внутри Live может работать другой парсер, чем вокруг вложения |
| Публичная страница | `server/src/services/renderhtml.ts`, `server/src/routes/shares.ts` | самостоятельная копия преобразований и схемы очистки |
| Табличные ячейки | `scanTables`, `appendInline` в `livePreview.ts` | собственное распознавание таблиц и ограниченный inline-рендерер |

Основная причина расхождений: текст многократно классифицируется независимыми правилами без единой информации «это код / текст / HTML / атрибут / ссылка». Последующий regex может обработать HTML, созданный предыдущим проходом. Отдельные исправления одной ветки не исправляют остальные.

## Результаты анализа 2026-10-29

Проверены существующие функции `renderMarkdown` и `renderNoteHtml` на синтетических строках; Live/Reading проверены в скрытом Electron с реальными CodeMirror decorations, `htmlBlockField` и `tableField`. Это проверки содержимого DOM и исходника, не визуальное сравнение пикселей с запущенным Obsidian. Временный браузерный скрипт удалён; входы и результаты зафиксированы ниже. Production-код в ходе этого анализа не изменялся.

### Воспроизведённые проблемы

| ID / приоритет | Пример | Фактический результат |
|---|---|---|
| R01 / P1 | `<u>x</u> <LS_BEN>-FIELD` | В Live/Reading остаётся `x -FIELD`: исправление `<LS_BEN>` работает на начале строки, но HTML-widget поглощает его внутри смешанной строки. Preview сохраняет литерал. |
| R02 / P1 | `prefix <u>x</u> suffix` | Live/Reading показывают теги текстом, хотя тот же `<u>` в начале строки превращается в подчёркивание. |
| R03 / P1 | таблица `a/b, ---/---, x/y` внутри fenced-блока | Live превращает пример кода в редактируемую таблицу; Reading тоже строит таблицу. `scanTables` не ограничен узлами Markdown-таблиц. |
| R04 / P1 | строка с четырьмя пробелами и `[[note]]`; четыре backtick вокруг вложенного блока из трёх | Web/server вставляют текст сгенерированного `<a ...>` внутрь code block. Защита кода через regex не учитывает все виды ограждений и отступов. |
| R05 / P1 | `\[[note]]` | Live создаёт ссылку; Web/server оставляют видимый обломок HTML-ссылки вместо корректного литерала. |
| R06 / P1 | inline code с `![[note]]`, при доступном resolver | `expandEmbeds` вызывает resolver и вставляет содержимое заметки до защиты code spans. |
| R07 / P1 | `![[note#Section]]` | Preview передаёт resolver только `note` и встраивает также раздел `Other`; якорь теряется. |
| R08 / P1 | `![x](folder/sub/image%20one.png)` | Web передаёт rawUrl `image one.png`, server — `folder/sub/image one.png`. Потеря пути создаёт риск выбора другого файла с тем же именем. |
| R09 / P1 | `before %%hidden%% after` | Preview скрывает комментарий; Reading оставляет его в DOM с классом `cm-comment` (CSS лишь меняет цвет); server выводит его обычным текстом. |
| R10 / P1 | `<span style="color: #ff0000">red</span>` | Preview превращает `#ff0000` внутри атрибута в ссылку-тег и ломает разметку; server удаляет style. Пробел после `:` существенен для воспроизведения. |
| R11 / P2 | `==marked==`, `- [/] partial`, `> [!note]- Title` | Preview поддерживает highlight/custom-task/fold, server оставляет `==`, не строит checkbox и включает `-` в заголовок callout. |
| R12 / P2 | `first` + один перенос + `second` | Preview создаёт `<br>`, server сохраняет soft newline без `<br>`. Нужно согласовать это с настройкой Strict Line Breaks. |
| R13 / P2 | `==mark==` и `~~strike~~` в ячейках | Live/Reading оставляют delimiters буквальным текстом. `appendInline` не поддерживает эти конструкции. |
| R14 / P2 | `text ^[note]` | Live/Reading лишь оборачивают исходный токен в superscript-класс; Web/server оставляют его текстом. Полноценного поведения inline-сносок нет. |

P1 означает первоочередные исправления исчезающего/неверного содержимого и нарушенных границ синтаксиса; это не оценка безопасности или утверждение о записи повреждённых файлов. Во всех браузерных пробах исходный текст оставался неизменным.

### Выявленные по коду зоны риска, ещё не подтверждённые полной матрицей

- YAML разбирается/сериализуется упрощёнными собственными функциями (`parseFrontmatter`, `serializeFrontmatter`, `frontmatterHtml`): проверить multiline scalars, quoted colon/comma, вложенность, даты и round-trip при редактировании свойств.
- HTML в Live очищается локальным blacklist, Preview/server — разными rehype-схемами. Проверить допустимые атрибуты, style/class, URL и вложенные элементы; не объявлять эквивалентность до тестов.
- Табличные разделители, escaped pipes, wikilink aliases и вложенное форматирование обрабатываются regex независимо от основной грамматики.
- Многострочная математика, Mermaid, nested callouts, reference links, HTML entities, CRLF, незакрытые конструкции и раскрытие при курсоре требуют отдельного корпуса.
- Подсветка использует дерево, а замена видимого текста — другие правила. «Красный тег» ещё не означает, что его нужно превращать в HTML.
- Внутренний `docs/obsidian-desktop-internals.md` относится к заявленной версии 1.12.7/macOS; это исторический материал, а не автоматически актуальный эталон пользователя.

## Источники эталонного поведения

- [Obsidian: HTML content](https://obsidian.md/help/html): ограничения HTML и обработки Markdown внутри него.
- [Obsidian: Basic formatting syntax](https://obsidian.md/help/syntax): escaping, комментарии, сноски и Strict Line Breaks. В частности, inline-сноски доступны в Reading, а не Live.
- [Obsidian Flavored Markdown](https://obsidian.md/help/obsidian-flavored-markdown): перечень расширений, включая block references.
- Локальные PRD FR-2 и `docs/obsidian-desktop-internals.md`, разделы 7–10, 19.

Не нужно «исправлять» все различия HTML/Markdown в сторону большего форматирования: часть ограничений самого Obsidian намеренная.

## Выбор подхода

1. **Добавлять regex-исключения.** Быстро для отдельных строк, но оставляет R01/R03/R10 и дрейф между режимами. Не подходит как основной план.
2. **Заменить Live целиком на HTML Preview.** Сближает вывод, но ломает модель редактирования, курсор, таблицы и измерение высоты. Не рекомендуется.
3. **Общий контракт диалекта + контекстные преобразования + разные адаптеры.** Рекомендуемый путь: сохраняет редактор и позволяет исправлять по одной группе с проверяемыми результатами.

Общий слой не должен хранить DOM, React, настройки сервера или доступ к vault. Сначала объединяются правила и тестовые случаи; выделение runtime-пакета — только вместе с первым реальным общим потребителем, без переноса всего `livePreview.ts` ради структуры.

## Порядок и ожидаемый результат

Сначала 1 → 2 → 3: закрыть исчезновение текста и обработку кода как разметки. Затем 4 → 5: согласовать режимы и цели ссылок. После этого 6 → 7: структуры и визуальная точность. Завершить 8.

Каждая задача — отдельный проверяемый результат. Не обещать «полную совместимость» по одному скриншоту или числу тестов: итоговый отчёт должен показывать покрытые варианты, оставшиеся отличия и версию Obsidian, с которой сравнивали.
