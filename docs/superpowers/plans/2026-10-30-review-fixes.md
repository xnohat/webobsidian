# Исправление шести замечаний ревью — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Делегирование — только по отдельному решению пользователя. Коммиты и push — только по явному запросу пользователя.

**Goal:** устранить шесть воспроизведённых дефектов аутентификации, сохранения и файловых операций без потери пользовательских данных.

**Architecture:** перенести проверку версии и изменение текста в одну серверную транзакцию; операции приложения над хранилищем выполнять через общую очередь изменений. Сохранение файла использует уникальный временный файл, переименование запрещает замену существующего назначения, копирование проверяет каждый реальный путь. На клиенте разделить закрытие вкладки, переименование и удаление.

**Tech Stack:** существующие TypeScript, Node.js, Express, React/Zustand, Vitest и node:test; новые runtime-зависимости не требуются.

**Spec:** `PRD.md`, разделы FR-1, FR-2, FR-3, FR-6, FR-12, FR-14; шесть замечаний ревью чата от 2026-10-30, зафиксированных ниже. Это предлагаемый план; реализация ещё не начата.

## Global Constraints

- Проверки выполняются на временных хранилищах; реальные заметки, конфигурация пользователя и развёрнутые установки не изменяются.
- Сохраняются форматы заметок, settings.json, API-ключи, штатные сильные резервные пароли и автоматический вход Electron.
- `baseVersion` в браузерном API и `base_version` в Agent API сохраняют названия и контракт; `''` означает создание только отсутствующего файла.
- Запись без версии остаётся совместимой с текущим API; действующая политика `WEBOBSIDIAN_AGENT_REQUIRE_VERSION` не ослабляется.
- Допустимые ссылки внутри `allowedRoots` продолжают работать; запрет всех ссылок не является исправлением R5.
- Рабочая модель — один серверный процесс на хранилище. Очередь гарантирует порядок операций этого процесса, но не превращает внешние записи Obsidian, Git или другого процесса в транзакции. Эти границы нужно явно документировать.
- Для простой и проверяемой реализации предлагается одна очередь на канонический корень хранилища. Это сериализует и независимые изменения, включая длительное копирование; чтения остаются параллельными. Более сложные блокировки отдельных путей и поддеревьев не нужны для этих шести исправлений.
- Путь хранилища и разрешённые корни фиксируются в контексте операции: ожидающая операция не должна после смены настроек записать данные в другое хранилище.
- Перед реализацией уточнить соответствующие контракты в `PRD.md`, отметить работу в `IMPLEMENTATION_PLAN.md`; по завершении обновить результаты проверок. Новые функции продукта в план не входят.

- [ ] Добавить управляемые конкурентные HTTP-тесты: две PUT с одним base version; две create-only с `''`; браузерная PUT одновременно с Agent PUT; два append; два find/replace; два алиаса одного файла. Ожидание CAS — `[200,409]`; append без версии сохраняет обе добавленные строки.
- [ ] Проверить очередь: следующая операция выполняется после ошибки, после завершения не остаются записи в таблице очередей. Проверить фиксацию исходного корня при ожидании.

- [ ] Перенести read/checkVersion/applyEdit/write внутрь `mutateFileText`. Для append также использовать этот read-modify-write. Сохранить ответы 404/409 и `currentVersion`, а индексы и автокоммит обновлять только после успешной записи.
- [ ] Включить в общую очередь публичные операции изменения файлов: binary write, rename, copy, remove, trash, restore и purge. Высокоуровневая операция получает очередь один раз; вложенные приватные действия её повторно не захватывают. Подбор имени загрузки и запись должны выполняться как одна операция.
