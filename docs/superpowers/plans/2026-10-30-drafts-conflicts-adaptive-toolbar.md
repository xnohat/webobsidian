# Черновики, разрешение конфликтов и адаптивная панель — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Делегирование, коммиты и push — только по отдельному запросу пользователя.

**Goal:** восстанавливать несохранённые документы после перезапуска браузера, разрешать конфликты версий без потери текста и сохранять доступность всех команд форматирования при любой поддерживаемой ширине редактора.

**Architecture:** локальный журнал черновиков в IndexedDB дополняет существующие очереди сохранений и серверную проверку версии. Клиент хранит базовую версию и текст, текущую редакцию и подтверждённое состояние; конфликт разрешается явным сравнением и повторной CAS-записью. Панель измеряет собственный контейнер, оставляет одну строку и переносит неуместившийся хвост команд в меню «Ещё».

**Tech Stack:** существующие TypeScript, React/Zustand, CodeMirror 6, Express, node:test/Vitest; браузерные IndexedDB и ResizeObserver. Для представления различий — совместимый с установленным CodeMirror пакет `@codemirror/merge`; версию и API проверить по официальной документации при реализации, зафиксировать в package-lock.json.

**Spec:** требования и решения пользователя в чате от 2026-10-30, формализованные в разделе «Согласованный результат» ниже; `PRD.md`; `docs/superpowers/specs/2026-10-29-full-editing-toolbar-design.md`. Зависимость: `docs/superpowers/plans/2026-10-30-review-fixes.md`.

**Статус:** основные функции реализованы по запросу пользователя, начав с задач 5–6. Результаты автоматических проверок и решения исполнения: `2026-10-30-drafts-conflicts-adaptive-toolbar-progress.md`. Ручные проверки масштаба/мобильной клавиатуры/Linux остаются отдельно отмеченными; непроверенные пункты не считаются пройденными.

## Согласованный результат и выбранные подходы

### 1. Восстановление черновиков

- Локально сохранять изменения редактируемых Markdown, TXT и Canvas. Для Canvas хранить полный валидный JSON документа; не пытаться сливать узлы как обычный текст.
- После перезагрузки или повторного открытия показывать доступный черновик и предлагать восстановление, сравнение либо удаление конкретного черновика. До выбора не запускать его отправку на сервер.
- Черновик удаляется автоматически только после подтверждения сохранения именно этой редакции. Ответ на старый запрос не удаляет более новый текст.
- Видимые состояния: изменено, сохранение, сохранено локально, сохранено на сервере, конфликт, ошибка локального/серверного сохранения. Статус доступен и на мобильном экране, где общая строка состояния скрыта.
- Выбран IndexedDB: асинхронные транзакции, отдельные записи документов и возможность хранить базовый текст. `localStorage` с полными документами блокирует ввод; серверные черновики не спасают при недоступном сервере.
- Это восстановление локальной работы, а не полный офлайн-клиент: автономная загрузка приложения, офлайн-поиск и очередь всех файловых операций сюда не входят.

### 2. Разрешение конфликтов сохранения

- Обычное сохранение редактора передаёт версию, полученную вместе с базовым текстом. При `409 version_conflict` локальный текст сохраняется, автоматические повторы записи этого документа останавливаются.
- Показывать локальный текст, актуальный серверный текст и редактируемый результат. Базовый текст используется для понимания изменений с обеих сторон. Действия: выбрать локальный/серверный фрагмент, отредактировать результат, сохранить отдельную копию, отложить решение.
- Результат сохраняется с версией показанного серверного документа. Новый конфликт не приводит к принудительной перезаписи: сохранить результат как черновик и обновить сравнение.
- Альтернатива «оставить целиком мою/серверную версию» полезна как дополнительная команда, но недостаточна для основного сценария. Не вводить автоматическое безусловное объединение текста.
- Canvas получает выбор целого документа или сохранение копии; повреждённый JSON нельзя отправить из интерфейса разрешения конфликта.
- Git merge-конфликты — отдельный последующий этап, описанный в конце. В этом плане завершённость пункта 2 означает конфликты сохранения браузер ↔ сервер, включая изменения через Agent API. Нельзя выдавать это за готовый Git merge UI.

### 3. Панель в одну строку с «Ещё»

- Пользователь выбрал одну строку с меню «Ещё», а не перенос на несколько строк.
- При достаточной ширине видны все настроенные команды; при сужении хвост уходит в `…`. Порядок пользователя сохраняется. Группа и составная кнопка цвета неделимы.
- Измерять область панели внутри редактора, а не только `window.innerWidth`. Открытие/закрытие и перетаскивание боковых панелей, split, масштаб, шрифты и изменение размеров иконок пересчитывают раскладку.
- Не уменьшать кнопки для вмещения. На очень узкой панели допустима единственная кнопка «Ещё» со всеми командами; минимальная поддерживаемая ширина контейнера — ширина этой кнопки с отступами.
- Меню сохраняет группы, состояния active/disabled, палитры, подписи и исходное выделение. Оно не обрезается контейнером и остаётся внутри видимой области браузера.
- Новое поведение по умолчанию — `overflow: 'menu'`; существующие явно сохранённые `scroll`/`wrap` оставить выбираемыми. При внедрении объяснить переключение старой сохранённой раскладки в настройках, не сбрасывать пользовательский набор команд.

## Исходное состояние и зависимости

- Предыдущий план содержит отчёт о выполненных R1–R6 и проверках. При старте сверить текущие файлы и результаты; не реализовывать повторно серверную очередь, уникальные временные файлы и безопасное закрытие вкладок.
- В `web/src/lib/store.ts` уже есть последовательные сохранения, счётчик редакции и защита close/rename/delete. Однако `saveActiveDraft()` вызывает `api.write(path, content)` без версии; базовый текст и локальный журнал не сохраняются.
- `api.read()` умеет вернуть `version`, `api.write()` принимает `baseVersion`. Нужно довести этот контракт до обычного редактора, а не только отдельных операций API.
- `StatusBar.tsx` выводит `Saving…` для любого `dirty`, что не различает ожидание, сетевую ошибку и локальное сохранение.
- `ToolbarSurface.tsx` выводит весь список; CSS панели задаёт горизонтальную прокрутку со скрытой полосой. В конфигурации есть `scroll`/`wrap`, но нет вычисляемого меню переполнения.
- Git sync имеет собственную обработку и отмену незавершённого merge; браузерный конфликт нельзя выдавать за сохранённый Git merge session.

## Global Constraints

- Работать с временными хранилищами. Не читать реальные заметки для тестов, не менять пользовательские настройки и не развёртывать приложение.
- Существующие незакоммиченные изменения не откатывать и не включать автоматически в эту работу. Перед началом снять `git status --short` и определить базовое состояние.
- Не менять формат заметок. IndexedDB — только клиентское хранилище; серверная конфигурация остаётся JSON, без нового серверного движка БД.
- Локальное хранение не равно серверному сохранению. Не обещать сохранность последних нажатий до завершения транзакции IndexedDB или после очистки данных браузера.
- Не включать содержимое черновиков в общую синхронизацию состояния интерфейса, логи, публичные страницы, аналитику и сообщения об ошибках.
- Черновики изолировать по серверной установке, хранилищу, пути и экземпляру вкладки браузера. После logout скрывать содержимое и останавливать синхронизацию; после входа показывать только черновики соответствующего хранилища. Приложение остаётся однопользовательским.
- `baseVersion`/`base_version`, `''` для create-only, 401/403/423 и правила locks сохраняются. UI конфликтов не обходит блокировки.
- CAS защищает операции одного серверного процесса. Внешние записи Obsidian/другого процесса между проверкой и записью остаются ограничением предыдущей архитектуры.
- Не удалять непереданные черновики по TTL. При нехватке места показывать ошибку и возможность экспорта; не освобождать место молча удалением пользовательского текста.
- Правки PRD и IMPLEMENTATION_PLAN относятся к реализации; при подготовке этого плана продукт и существующие документы не изменять.

## Порядок, границы завершения и следующий этап

Основной порядок: **1 → 2 → 3 → 4 → 5 → 6 → 7 → 8**. Блок панели 5–6 независим от хранения и может выполняться первым, если пользователь решит сначала исправить видимую проблему; это не разрешение на параллельное делегирование.

Готовность: черновик восстанавливается из постоянного браузерного хранилища; обычное сохранение использует CAS; конфликт не теряет исходный текст и ручной результат; каждая команда панели доступна при изменении ширины контейнера; проверки и документация отражают фактический результат.

**Отдельный последующий этап: Git merge UI.** Перед его реализацией нужен самостоятельный план с серверным контрактом: сохранять base/ours/theirs до текущего abort/recovery, выдавать устойчивый conflict-session token, проверять HEAD/MERGE_HEAD и версии файлов перед применением; согласовать блокировку auto-sync/auto-commit, восстановление после рестарта, binary/rename/delete conflicts, stage/commit и отмену. Повторно использовать визуальный diff задачи 4, но не его CAS-протокол как замену Git-транзакции. Этот этап не входит в критерии готовности текущего плана и не считается выполненным после реализации обычного сравнения заметок.

Коммиты, push, публикация, развёртывание и изменения реального хранилища в этот запрос не входят.
